# Model Card — Student Journey Intelligence Engine

Model version: `20260924-081650` (soft-voting ensemble of a tuned Logistic Regression
and a tuned Random Forest, calibrated). Regenerate this version by running
`python -m student_journey.models.train`; every number on this page is copied from an
actual run's output (`models/model_metadata.json`, `models/evaluation_report.json`),
not estimated.

This model card follows the spirit of Mitchell et al., "Model Cards for Model
Reporting" (2019). It documents a **portfolio/educational project**, not a system in
production use anywhere.

## Intended use

- **Decision support for academic advisors and student-success staff**, to help
  prioritize which students to proactively reach out to each term.
- Intended to surface a ranked list (via the `low`/`medium`/`high` risk category) and
  the top statistical factors behind a given prediction, as **one input among many**
  to a human advisor's judgment.
- Intended to run on the synthetic dataset generated by this repository, or on data
  with an equivalent, properly-governed real-world schema and appropriate
  institutional/privacy approval — not on real student data as-is.

## Non-intended use

- **Not** intended for automated decisions with no human in the loop — admissions,
  financial aid eligibility, academic probation, disciplinary action, or any action
  that affects a student's status.
- **Not** validated on, fit to, or representative of any real university, and must
  not be described or deployed as if it were.
- **Not** intended to be the sole basis for withholding support, resources, or
  opportunity from any student. A "high risk" score is a prompt to offer more
  support, not a prediction to act on punitively.
- **Not** fit for use with real, identifiable student data without a separate privacy,
  security, and fairness review appropriate to that context (IRB/FERPA-equivalent
  processes, access controls, consent, etc. — see "Ethical risks" below).

## Dataset

- **Entirely synthetic and fabricated** — generated by
  [`generate_synthetic_data.py`](../src/student_journey/data/generate_synthetic_data.py)
  via a forward-in-time stochastic simulation of student enrollment, including
  stop-out-and-return (gap-term) behavior. No real student, institution, or record
  contributed to any value in this dataset. Full field definitions:
  [`data/DATA_DICTIONARY.md`](../data/DATA_DICTIONARY.md).
- 4,000 simulated students, 17,581 student-term rows, 16,328 labeled rows (the rest
  excluded as graduating or right-censored — see the data dictionary's "Target
  construction and leakage guardrails" section).
- Class balance: ~73% persisted / ~27% did not persist to the immediate next term, on
  the held-out test split. (This shifted from an earlier ~86%/14% split when gap-term
  simulation was added — stop-out-then-return students are now correctly counted as
  not persisting to the *immediate* next term, even though they return later.)
- Time-aware split by calendar term: train `term_order<=12`, validation `13-14`, test
  `>14` — training never has access to a student's outcome in a "future" calendar
  term relative to what it's predicting.
- **(planned, not implemented)** Benchmarking this modeling approach against the real,
  already-anonymized UCI "Predict Students' Dropout and Academic Success" dataset was
  considered during planning but never built — no such benchmark exists in this repo.

## Model

- **Selected model: a soft-voting ensemble** (`sklearn.ensemble.VotingClassifier`,
  `voting="soft"`) of a Logistic Regression and a Random Forest, each independently
  hyperparameter-tuned with Optuna (15 trials for Logistic Regression's `C`; 25 for
  Random Forest's `n_estimators`/`max_depth`/`min_samples_leaf`/`max_features` —
  see `N_TUNING_TRIALS` in [`train.py`](../src/student_journey/models/train.py)).
  The ensemble won on validation ROC-AUC (0.706) over the individually-tuned
  Logistic Regression (0.704) and Random Forest (0.704) — a genuine, if narrow,
  win, not a foregone conclusion; the comparison is logged for every run. XGBoost is
  implemented and tuned identically but was environment-blocked on the local
  development machine (missing `libomp`); it runs in the Docker image (Phase 7) and
  joins the ensemble automatically whenever it's available.
- **Calibrated**: the ensemble is wrapped in `sklearn.calibration.CalibratedClassifierCV`
  (Platt/sigmoid scaling, fit on the validation set only) to correct a measured
  distortion from `class_weight="balanced"` — see Metrics below.
- **Input features** (19 total — see `FEATURE_COLUMNS` in
  [`train.py`](../src/student_journey/models/train.py)): academic performance (GPA,
  GPA change, academic momentum), credit load and completion
  (attempted/completed/cumulative/rate), enrollment behavior (intensity, withdrawals,
  repeats), support signals (advising contact, financial aid), and program/entry type.
- **Deliberately excluded from input features:** `age_band`, `gender`,
  `first_gen_flag`, `distance_from_campus_band` — synthetic demographic proxy fields
  kept in the dataset only to evaluate subgroup performance after the fact (see
  "Fairness" below), never fed to the model as predictive inputs. This is a design
  choice to avoid encoding indirect discrimination into the score, not an artifact of
  the data.
- Experiment tracking: MLflow (`mlruns/`, experiment `student_persistence`) — logs
  every tuned candidate, the ensemble, and the final calibrated model, including
  Optuna's best hyperparameters per model type.
  Preprocessing and model are one serialized artifact
  (`models/model_pipeline.joblib`) so there is no train/serve skew.

## Metrics (held-out test set, 2,990 rows, term_order > 14)

| Metric | Value |
|---|---|
| Precision | 0.767 |
| Recall | 0.946 |
| F1 | 0.847 |
| ROC-AUC | 0.689 |
| Average precision | 0.836 |
| Brier score | 0.177 (calibrated) |

Confusion matrix: TN=180, FP=628, FN=118, TP=2064.
Plots: [`confusion_matrix.png`](screenshots/confusion_matrix.png),
[`calibration_curve.png`](screenshots/calibration_curve.png) (now shows both curves,
before vs. after calibration),
[`shap_global_importance.png`](screenshots/shap_global_importance.png).

**Calibration (fixed):** `class_weight="balanced"` (needed for class imbalance)
measurably distorted predicted probabilities. This is now corrected:
`CalibratedClassifierCV` improved the test-set Brier score from **0.208 to 0.177** —
a real, verified improvement, not an assumption (see the before/after calibration
curve). Calibration is a monotonic remapping, so it changes the probabilities shown
but not the model's ranking (Spearman rank correlation between raw and calibrated
probabilities is exactly 1.0), which is why risk-category thresholds — the
60th/90th percentile of the model's own risk-score distribution on the validation
set (`risk_thresholds` in `model_metadata.json`: low_max=0.297, medium_max=0.517) —
are unaffected by the fix. On the test set this produces a real, monotonic gradient:
students the model calls "low risk" actually didn't persist 18.9% of the time;
"medium risk" 36.3%; "high risk" 62.6%.

**Fairness (subgroup performance, synthetic proxies only):** ROC-AUC by subgroup
ranges from about 0.622 to 0.719 across `age_band`, `gender`, `first_gen_flag`, and
`distance_from_campus_band` values on the test set (full numbers in
`models/evaluation_report.json`, regenerate via
`python -m student_journey.models.evaluate`). **This demonstrates the subgroup
evaluation method — it is not evidence about real-world fairness of anything**,
since every demographic value here is fabricated and the underlying data-generating
process was not designed to model any real bias pattern.

**Error analysis:** full breakdown in `models/evaluation_report.json`, regenerated by
`python -m student_journey.models.evaluate` on every run — not reproduced here since
it changes with the model; see that file's `error_analysis` key for the current
run's false-positive/false-negative feature profiles.

## Explainability

Per-prediction explanations use the SHAP explainer matched to the model type that's
actually selected (see
[`shap_utils.py`](../src/student_journey/explainability/shap_utils.py)):
`shap.LinearExplainer` for a linear model, `shap.TreeExplainer` for a tree ensemble,
or — for the current ensemble model — a model-agnostic `PermutationExplainer`
operating on raw features (each ensemble member preprocesses internally, so there's
no single shared transform to explain in). The additive score's units (log-odds vs.
probability) are **detected empirically per model** rather than assumed, since they
genuinely differ by algorithm, and reported in every explanation's `score_scale`
field. The additivity property (`base_value + sum(shap_values)` reconstructs the
model's own raw score exactly) is checked by an automated test
(`tests/test_explainability.py`) against whichever model is currently selected, not
just asserted for one model type. Global importance (`shap_global_importance.png`)
shows term GPA, advising contact, and cumulative GPA as the dominant factors —
consistent with how the synthetic data-generating process was designed, which is a
useful sanity check that the model learned the intended signal rather than a
spurious artifact, and that this holds across the different model types this project
has selected over its development (Logistic Regression, then this ensemble).

**This model identifies statistical patterns in historical-style data. It does not
determine, guarantee, or fully explain any individual student's actual future.**
Every explanation and API response repeats this.

## Limitations

- Entirely synthetic data; no real-world validation has been or could be performed.
  Metrics describe how well the model recovers the patterns *this simulation* was
  designed to contain, not real-world predictive accuracy.
- Demographic proxy fields have low cardinality and were hand-authored, not fit to
  any real population's distribution — subgroup results should not be generalized.
- Single simulated "institution" with one set of enrollment dynamics; no
  cross-institution variation is modeled.
- Time-aware split covers a 20-term synthetic calendar; long-run drift over many
  more real academic years is untested. Real, PSI-based feature-drift monitoring is
  implemented (`GET /monitoring/drift`, the dashboard's Monitoring tab — see Phase 10
  in the README) and activates automatically once ~30+ requests have been logged; it
  has been verified to correctly flag a deliberately anomalous traffic pattern, but
  has never observed genuine multi-year drift, since no real deployment has run that
  long. Below the logging threshold it falls back to illustrating the drift-check
  *method* using the train/test split as a stand-in.
- The intervention-impact analysis (`analysis/intervention_simulation.py`, the
  dashboard's Intervention Impact tab) is a sensitivity analysis over **assumed**
  participation-rate and effect-size parameters — this dataset has no recorded
  outreach history to estimate a real causal effect from. Treat its output as a
  business-case sketch for discussion, never as a validated prediction of program
  impact.
- The ensemble/Permutation explainer path is slower than the closed-form
  `LinearExplainer`/`TreeExplainer` paths (roughly 10-20x more model evaluations per
  explanation) — acceptable for this project's request volume, but a real
  high-throughput deployment using an ensemble would want to budget for that cost or
  cache explanations.
- Hyperparameter search spaces (Optuna) are modest (15-25 trials per model type),
  sized to keep local development runtime reasonable rather than to exhaustively
  search; a production retraining job could afford a larger budget.

## Ethical risks

- **Automation bias / over-reliance:** a risk score can be mistaken for a verdict.
  Mitigation: this model card, the API disclaimer, and the dashboard notice all
  restate that the model finds patterns, not futures, and that it's meant for human
  review, not automated action.
- **Punitive misuse:** flagging "high risk" must not translate into reduced
  support, opportunity, or access — that would also create a feedback loop where the
  intervention itself causes the predicted outcome. Intended use is *more* support,
  never less. The intervention-impact analysis exists to support exactly that kind of
  resourcing conversation, not to justify withholding anything.
- **Fairness risk if retrained on real historical data:** real institutional data
  often encodes historical inequities (e.g., under-resourced advising for some
  groups). A model trained on such data can reproduce or amplify those patterns even
  without demographic features as direct inputs, since other features can correlate
  with them. Subgroup evaluation (as demonstrated here, on synthetic data) is
  necessary but not sufficient — real deployment needs a fairness review with
  domain and legal expertise before use.
- **Privacy:** this project uses no real student data. A real deployment would need
  data minimization, access controls, consent processes, and retention limits
  appropriate to student-record privacy law (e.g. FERPA in the US) — entirely out of
  scope for and not implemented by this repository. The API's optional key-based auth
  and rate limiting are a starting point for access control, not a substitute for
  that review.
- **Drift:** implemented — `GET /monitoring/drift` and the dashboard's Monitoring tab
  compute the Population Stability Index per feature against the training
  distribution once enough requests have been logged (Phase 10). What's still not
  implemented: an automated *response* to detected drift (alerting, a retraining
  trigger, or automatic model rollback) — detecting drift and acting on it are
  different problems, and only the former is built here.
